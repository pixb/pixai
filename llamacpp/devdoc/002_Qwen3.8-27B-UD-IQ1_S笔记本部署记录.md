## 3. 模型核对

`./build/bin/llama-gguf models/Qwen3.8-27B-UD-IQ1_S.gguf r`:

- `general.name = Qwen3.8-27B`, `quantized_by = Unsloth`, `file_type = 24`(IQ1_S)
- 架构: `qwen35`(**Qwen3.5 混合架构: attention + SSM/Mamba**, 含 `ssm.*`、`full_attention_interval` KV)
- `block_count = 64`, `embedding_length = 5120`, head 24 / KV 4
- `nextn_predict_layers = 0` → **非 MTP** 基础模型
- 851 张量, 无 `blk.64.nextn.*` 头 → **普通 llama.cpp 即可加载, 无需 turboquant fork**
- GGUF v3, **alignment = 32**

> 踩坑: 手写 GGUF 元数据解析脚本前 32 字节 off-by-one, 因为该文件 kv 段按 32 字节对齐; llama-gguf 的 `alignment: 32` 能正确读取。

## 5. 启动与关键参数

脚本: `start_server_qwen38_27b_iq1s.sh` (端口 **8081**, 与 3090 主服务 8080 区分)

```bash
SERVER="./build/bin/llama-server"
MODEL="./models/Qwen3.8-27B-UD-IQ1_S.gguf"
CTX=16384   # 实测可全量 offload
NGL=99      # 全层 GPU

-c 16384 -ngl 99 --parallel 1 --flash-attn on
--cache-type-k/v q8_0        # SSM 混合架构 KV 小, 8bit 缓存无压力
--chat-template-file ./Qwen-Fixed-Chat-Templates/chat_template.jinja
--reasoning-format deepseek --reasoning-preserve --reasoning-budget -1
-t 12 --batch-size 512 --ubatch-size 512
```

> 复用 3090 上验证过的 Qwen-fixed 模板(submodule 已 init), 思考单独提取到 `reasoning_content`。

## 6. 实测结果 (全量 GPU offload, RTX 4070 Laptop 8GB)

### 6.1 显存/资源

| 上下文 | VRAM used | VRAM free | 备注 |
|--------|-----------|-----------|------|
| 8192 | 7.18 GB | ~924 MB | 成功 |
| **16384** | **7.28 GB** | **672 MB** | 成功, 推荐默认 |

- llama-server RSS 约 **2.4 GB**, GPU 空闲功耗 ~22W / 140W, 温度 ~67°C

### 6.2 推理速度 (`/v1/chat/completions`)

| 场景 | Prompt 速度 | 生成速度 |
|------|------------|---------|
| 首测 (8K, 128 tokens) | 104.5 tok/s | **32.4 tok/s** |
| 长问 (8K, 1024 tokens) | 121.8 tok/s | **31.9 tok/s** |
| 16K 上下文 | 54~120 tok/s | **30.4~32.2 tok/s** |

- 生成稳定 **~32 tok/s**(全 offload 下受 IQ1_S 极端量化算子限制, 非带宽瓶颈)
- 对比 3090 Q3_K_M ~62 tok/s → 笔记本约为一半

### 6.3 质量观察 (IQ1_S 特性)

- 温度 ≥1.1 时简单问答正常: `中国的首都是北京。` / `1+1等于2。` ✅
- **低温(0.6)或复杂任务下易陷入重复循环**(如 "Viny Viny Viny..."、思考检索过长) → 配 `temperature≈1.1~1.2`
- **thinking 会吃满 max_tokens** 导致 `content` 为空(finish_reason=length): 输入侧说明"不要思考"或提高 max_tokens 可缓解
- 编码/长文本任务退化最严重, 属 1-bit 量化固有代价

## 8. 结论与建议

- **可行**: IQ1_S 27B 在 8GB 显存下可全量 GPU offload, ~32 tok/s, 简单问答可用
- 想要更高质量可换 `Q3_K_M`(12.9GB, 3090 同款): 笔记本需 CPU offload(~10GB 权重落内存), 速度会明显下降
- 生成侧建议恒定 `temperature≈1.1~1.2`, 客户端注意传 `max_tokens`(`-n -1` 不截断但 thinking 会占满)

## 9. TurboQuant turbo3 KV 缓存 (上下文显存优化)

### 9.1 背景

默认 `q8_0` KV 缓存 **~40B/token**(实测 8192→6955MiB, 16384→7277MiB)。8GB 显存中权重+计算缓冲 ≈ 6.6GB, 留给 KV 的预算约 1.4GB → **q8_0 全载荷上限约 28K**。

### 9.2 编译 fork

```bash
git clone https://github.com/TheTom/llama-cpp-turboquant.git llama-cpp-turboquant-mtp
git -C llama-cpp-turboquant-mtp checkout tags/feature-turboquant-kv-cache-b10465-fca3093
cmake -B llama-cpp-turboquant-mtp/build -DGGML_CUDA=ON -DLLAMA_CURL=ON -DCMAKE_BUILD_TYPE=Release \
      -DCUDAToolkit_ROOT=/opt/cuda -DCMAKE_CUDA_COMPILER=/opt/cuda/bin/nvcc \
      -DGGML_CUDA_FA=ON -DGGML_CUDA_GRAPHS=ON
cmake --build llama-cpp-turboquant-mtp/build --config Release -j 16 --target llama-server llama-gguf
```

- 与 3090 服务器(devdoc/001)同款 fork 与 tag, 支持 qwen35 架构
- 本机 CUDA 13.3 + sm_89 编译通过(约 5 分钟)

### 9.3 关键行为: auto-asymmetric

```
llama_kv_cache: auto-asymmetric: GQA ratio 6:1 (n_head=24, n_head_kv=4)
  — upgrading K from turbo3 to q8_0 to prevent quality degradation.
```

GQA 6:1 下 K 缓存自动保持 q8_0, **仅 V 用 turbo3**(3.5bit), 兼顾长上下文质量。

### 9.4 上下文缩放实测 (全量 GPU offload, 8GB)

> 模型原生上下文 **262144 (256K)**。限制完全在显存。

**关键坑: `--load-mode mlock` 在 WSL2 上会 Kill 进程。**
mlock 需锁住大块 RAM, WSL2 的 `RLIMIT_MEMLOCK` 很小 → 日志报 `failed to mlock ... Cannot allocate memory` 后进程被 Killed。
之前 64K/96K 不稳定全因于此, **去掉 mlock 后 64K 即稳定**。已在脚本中移除。

> fork 的 KV 缓存为惰性分配, 启动瞬间 VRAM 数字会误导, 需加载完成后实测。

| 方案 | 上下文 | VRAM used | 余量 | 稳定性 |
|------|--------|-----------|------|--------|
| vanilla q8_0 | 16384 | 7.28 GB | ~672 MB | ✅ 稳定 (封顶约 28K) |
| turbo3 | 32768 | 7.60 GB | ~585 MB | ✅ 稳定 |
| turbo3 | **49152(48K)** | **7.63~7.77 GB** | **~182~560 MB** | ✅ 稳定, **默认推荐** |
| turbo3 | **65536(64K)** | **7.85~7.90 GB** | **~51~103 MB** | ✅ 稳定(去 mlock 后), 实际可用上限 |
| turbo3 | 98304(96K)+ | - | - | ❌ 超限被 Killed |

- 64K 三轮 181~256 token 连续长生成实测稳定: 31.6~32.1 tok/s, 中途无 OOM
- **CPU offload 不划算**: 混合架构(SSM)KV 本就很小的, NGL 60 只省 ~50MB 显存, 却掉到 18 tok/s(RAM 多占 ~500MB)
- 生成速度不受上下文影响: **~31.6~32.9 tok/s**(与 q8_0 相同), prompt ~89 tok/s
- turbo3 收益: **16K → 48K(推荐)/64K(上限)**, 约为原 3~4 倍上下文

### 9.5 使用

脚本: `start_server_qwen38_27b_iq1s_turbo3.sh`(推荐, 端口 8081)

```bash
SERVER="./llama-cpp-turboquant-mtp/build/bin/llama-server"
CTX=49152
--cache-type-k turbo3 --cache-type-v turbo3
--flash-attn on          # 勿加 --load-mode mlock: WSL2 下会 Kill 进程
```

回退: `start_server_qwen38_27b_iq1s.sh`(vanilla build, q8_0, 16K)

## 10. 防死循环 (IQ1_S 关键修复)

### 10.1 症状与根因

- **症状**: 使用中陷入死循环——要么反复输出同一短语("Viny Viny Viny..."), 要么思考无限展开占满 max_tokens 且永远不输出正文(content 为空)
- **根因**:
  1. IQ1_S(1-bit) 模型退化严重, 默认采样(temp 0.8, 无复读惩罚)极易触发复读
  2. **思考层是最大循环来源**: `--reasoning-budget -1`(无限)时思考可以无限跑; 限预算(512/1024)虽然能截断思考, 但 Qwen 修复模板在该模型上**截断思考后不输出正文**(content 直接为空); budget 0 更糟(整段无输出)

### 10.2 实测结论: 关闭思考层 + 硬采样

最终采用组合(**实测多轮/开放式均正常收尾, 无复读**):

```bash
--reasoning off        # 关键: 彻底关闭思考层
--temperature 1.2      # 避开 0.8 的复读阈值
--min-p 0.05           # 过滤低概率噪声
--repeat-last-n 512    # 惩罚窗口 512 (默认 64 太短)
--repeat-penalty 1.35  # 主动惩罚复读
```

实测对比 (同一易循环 prompt):

| 配置 | 结果 |
|------|------|
| 原配置 (思考无限, 默认采样) | ❌ 死循环, content 空 |
| reasoning-budget 512 | ⚠️ 思考 512 截断但不输出正文 |
| reasoning-budget 0 | ❌ 整段无输出 |
| **reasoning off + 硬采样** | ✅ finish=stop, 280 字正文, 重复度 ngram(3)≈3 |

- 简单问答: content 正常 ✅ 多轮对话: `2+3`→`5`, finish=stop ✅
- 生成速度: ~28~30 tok/s(不受影响)
- 两个启动脚本均已写入该参数组

> 已在脚本中移除 mlock(见 §9.4)。该组参数是 IQ1_S 可用的前提, 换更高量化(Q3_K_M)时可放宽。
