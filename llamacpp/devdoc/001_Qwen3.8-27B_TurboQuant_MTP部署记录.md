## 1. 背景与目标

本项目围绕 llama.cpp + TurboQuant 构建本地 LLM 推理服务。本次任务核心:

1. **在不破坏现有环境的前提下**,引入新版 fork 以支持 **MTP(多 token 预测)投机解码** 和 **多模态视觉(带 mmproj)**。
2. 现有模型 `Qwen3.8-27B-*` 是 **MTP 版 GGUF**(含 `blk.64.nextn.*` 张量头),而旧版 build(b9082)**无法加载**这些张量(**缺失张量报错**),必须升级。
3. 保证旧方案(`start_server_turboquant_128k.sh` + Qwen3.6)始终可用,作为回退。

这决定了必须更换新 build。

## 4. 编译方案

### 4.1 为什么需要新 build

| 需求 | 旧 build (b9082) | 新 build (fca3093) |
|------|-------------------|--------------------|
| 加载 MTP 版 GGUF | ❌ 张量缺失报错 | ✅ |
| MTP 投机解码 | ❌ | ✅ `--spec-type draft-mtp` |
| 多模态 mmproj | ❌ (LLaVA 架构不支持 qwen35 视觉) | ✅ `--mmproj` |
| turbo3 KV 缓存 | ✅ | ✅ |

结论: **MTP 版模型直接用新 build,不需要下载 no-MTP 版。**

### 4.2 编译命令

```bash
# 克隆新版 fork(与旧版分离,不影响现有环境)
git clone https://github.com/TheTom/llama-cpp-turboquant.git llama-cpp-turboquant-mtp
cd llama-cpp-turboquant-mtp
git checkout feature-turboquant-kv-cache-b10465-fca3093

# 启用 CUDA
cmake -B build -DGGML_CUDA=ON -DLLAMA_CURL=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j --target llama-server llama-gguf

# 产物
# build/bin/llama-server  (ELF x86-64, 动态链接)
# build/bin/llama-gguf    (元数据/张量查看工具)
```

### 5.2 主脚本 `start_server_qwen38_27b.sh`

```bash
SERVER="./llama-cpp-turboquant-mtp/build/bin/llama-server"
MODEL="./models/Qwen3.8-27B-Q3_K_M.gguf"
MMPROJ="./models/mmproj-BF16.gguf"

CONTEXT_SIZE=200000
BATCH_SIZE=512

export LD_LIBRARY_PATH="$(cd "$(dirname "$SERVER")" && pwd):/opt/cuda/lib64:$LD_LIBRARY_PATH"
```

关键参数逐一说明:

| 参数 | 值 | 说明 |
|------|-----|------|
| `-c 200000` | 200K | 上下文窗口(平时改为 131072 或按需) |
| `-n -1` | 无限 | **默认最大输出 token,改为 -1 避免截断**(客户端可传 max_tokens 单独控制) |
| `-t 12` | 12 | CPU 线程数 |
| `-ngl 99` | GPU 层数 | 全部层上 GPU |
| `--parallel 1` | 1 | 并发槽位 |
| `--cache-type-k/v turbo3` | TurboQuant | 3.5bit KV 缓存优化 |
| `--flash-attn on` | - | Flash Attention |
| `--load-mode mlock` | - | **锁定内存(替代已弃用的 --mlock)**。旧版此参数显示 DEPRECATED 警告,新 build 已移除,必须用新写法 |
| `--batch-size 512` / `--ubatch-size 512` | - | 批处理 |
| `--chat-template-file ./Qwen-Fixed-Chat-Templates/chat_template.jinja` | - | **Qwen 修复版 jinja 模板**(froggeric v22.1,修复官方模板空 think/KV 失效/工具卡死问题,见 §8.5) |
| `--reasoning-format deepseek` | - | **思考提取到 `reasoning_content` 字段**,防思考泄漏进正文、中断工具调用 |
| `--reasoning-preserve` | - | 保持历史思考块,保证 KV 前缀缓存 100% 命中 |
| `--reasoning-budget -1` | -1 | 无限思考预算(原 `0` 关闭思考,与修复模板默认 enable_thinking 冲突) |
| `--spec-type draft-mtp` | - | **启用 MTP 投机解码** |
| `--spec-draft-n-max 3` | 3 | 每次最多预测 3 个 token |
| `--spec-draft-p-min 0.75` | 0.75 | 草稿接受概率下限 |
| `--mmproj ...` | - | **多模态视觉投影层** |
| `--host 0.0.0.0 --port 8080` | - | 监听地址 |
| `--log-disable` | - | 关闭详细日志(排障时可去掉) |

### 6.4 多模态视觉(重要坑)

> **注意**: 本会话先后遇到两个不同 build 的图片格式用法,已实测厘清:
> - **旧 b9082**(Qwen3.6 era): `image_url` 被废弃,`{"type":"image","image":{"url":...}}`
> - **当前 fca3093**(llama-cpp-turboquant-mtp,本脚本): 走 `server-common.cpp`(OpenAI 路径),**只接受标准 `image_url`**,`image` 字段报 `400: unsupported content[].type`
>
> **结论: 当前 build 必须用 OpenAI 标准 `image_url` + data URL**,即下面的写法:

```python
import base64, json, urllib.request
b64 = base64.b64encode(open("/path/to/img.png","rb").read()).decode()
payload = {
  "messages":[{"role":"user","content":[
     {"type":"text","text":"What is shown in this image? Be brief."},
     {"type":"image_url","image_url":{"url":f"data:image/png;base64,{b64}"}},
  ]}],
  "max_tokens":100, "temperature":0.5,
}
```

错误写法返回 400(当前 build):
```
{"error":{"code":400,"message":"unsupported content[].type",...}}
```

实测: 模型正确识别"macOS 终端窗口(pyenv/python 版本切换)" ✅

> 提示词 token 注意: 图片会编码为 ~2000 tokens/张, 上下文需留够。
>
> 另: 日志提示 Qwen-VL 建议加 `--image-min-tokens 1024` 提升 grounding 精度,如需可加。

## 8. 已知坑与教训

### 8.1 pkill 会卡住 shell(重要)

```bash
# ❌ 会匹配自身命令行, 导致 shell 卡死
pkill -f llama-server
# ✅ 用字符类技巧规避自身匹配
pkill -9 -f '[l]lama-server'
```

### 8.2 后台启动防阻塞

```bash
setsid ./xxx.sh </dev/null >/tmp/log 2>&1 &
# 或 nohup ./xxx.sh </dev/null >/tmp/log 2>&1 & disown
```

### 8.3 参数版本差异

| 旧写法 | 新写法 | 原因 |
|--------|--------|------|
| `--mlock` | `--load-mode mlock` | 新版移除并告警 |
| `-n 512` | `-n -1` | 默认 512 会截断长回复, Hermes 等客户端报 `finish_reason='length'` |
| `image_url` 字段 | `image` 字段 + data URL | OpenAI 兼容层弃用旧字段 |

### 8.4 GGUF 解析踩坑

- 早期解析用错 GGUF 类型表(把 v2 表当 v3)导致 `ValueError: type 12` 等。
- 实际 v3 类型表见 3.2 节。

### 8.5 Qwen-Fixed-Chat-Templates 修复模板引入

来源: `Qwen-Fixed-Chat-Templates/`(froggeric v22.1,Apache-2.0),单一通用模板同时覆盖 Qwen 3.5/3.6/3.8。

官方 Qwen3.8 模板在本地推理的已知缺陷(该包修复):
1. 默认 `xhigh` 思考耗尽 `max_tokens` 却返回空内容 → 模板默认 `medium`
2. 多轮对话注入空白 ` thinking` 块污染 → 干净提取思考
3. `enable_thinking=false` 直接抛异常 → 恢复快模式
4. JSON 字符串工具参数导致模板崩溃 → 通用解析
5. 深层 Jinja 嵌套拖慢 llama.cpp 80% → AST 扁平化

引入方式(本脚本已加):
```bash
--chat-template-file ./Qwen-Fixed-Chat-Templates/chat_template.jinja \
--reasoning-format deepseek \   # 思考 → message.reasoning_content
--reasoning-preserve \           # 保留历史思考块, KV 前缀缓存
--reasoning-budget -1 \          # 无限思考(原来 0 关思考, 冲突)
```

实测效果:
- 文本回复: 思考在 `reasoning_content`, 正文干净(`17*23` → 思考完整/答案"391")
- 视觉兼容: 多模态正常(模板含 vision_id 逻辑)
- 无性能劣化, MTP 接受率提升至 89%

诊断工具:
```bash
python3 Qwen-Fixed-Chat-Templates/scripts/check_applied.py <模型或GGUF>
```
